# Feature Specification: Q&A Response Ingestion & Storage

**Feature Branch**: `001-qa-response-ingestion`
**Created**: 2026-04-12
**Status**: Draft
**Input**: User description: "First foundational spec for AnswerGuard — how Q&A response data gets captured and stored so PMs can review and annotate it."

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Historical Data Import (Priority: P1)

A developer at a company using an existing AI agent product wants to onboard AnswerGuard. Their agent system has six months of Q&A history sitting in a BigQuery dataset. The developer wants to pull that history into AnswerGuard so their PM can immediately start reviewing past responses and building guidelines — without waiting for new responses to accumulate.

**Why this priority**: Without historical data, the PM faces an empty interface on day one. A bulk import gives immediate value and shortens the time-to-first-annotation to hours, not weeks. This is the primary adoption driver.

**Independent Test**: Can be fully tested by configuring the source connector with a test database containing 100 Q&A records, running the import, and verifying all 100 records appear in AnswerGuard's storage with correct fields. Delivers standalone value: a populated dataset ready for PM review.

**Acceptance Scenarios**:

1. **Given** a developer has provided a source database connection string and field mapping configuration, **When** they trigger a historical import, **Then** all Q&A pairs are read from the source database and written to AnswerGuard's own database without modifying the source.
2. **Given** the historical import has run before, **When** it is triggered again, **Then** previously imported records are not duplicated — only new records are added.
3. **Given** the source database is unavailable mid-import, **When** the connection fails, **Then** already-imported records are retained, the error is logged with the last successfully imported record, and the import can be resumed from where it stopped. Resume is triggered by re-calling `POST /v1/ingest/import` for the same `source_system_id` when a `FAILED` run exists — no separate endpoint is required.
4. **Given** a record in the source database has missing required fields (e.g., no answer text), **When** the import processes it, **Then** the record is skipped, logged as invalid, and the import continues processing remaining records.

### User Story 2 - Runtime Response Capture via SDK (Priority: P2)

The same developer now wants every new response generated by the agent system to automatically appear in AnswerGuard as it happens — without the PM needing to wait for a batch import. The developer adds a few lines to the agent pipeline using the AnswerGuard SDK.

**Why this priority**: Runtime capture is the operational steady-state after initial onboarding. It ensures the PM always has access to the latest responses. However it depends on the integration being set up, which requires the core storage layer (P1) to work first.

**Independent Test**: Can be tested by sending a single question/answer pair through the SDK and verifying it appears in AnswerGuard's storage with all metadata intact. Delivers standalone value: a live feed of new responses for ongoing PM review.

**Acceptance Scenarios**:

1. **Given** a developer has integrated the SDK into their agent pipeline, **When** a response is generated, **Then** the Q&A pair is captured and stored in AnswerGuard without adding more than 50ms of overhead to the response path (p95).
2. **Given** the AnswerGuard storage system is temporarily unavailable, **When** a response flows through the SDK, **Then** the original response is returned to the end user unaffected — the capture failure is logged silently and does not block the user.
3. **Given** the SDK captures a response, **When** the pair is stored, **Then** it includes: the question text, the answer text, a timestamp, the source system identifier, and any metadata fields passed by the developer (e.g., topic, session ID, user segment).
4. **Given** a developer is using the REST API instead of an SDK, **When** they POST a Q&A pair to the capture endpoint, **Then** the pair is stored with the same guarantees as SDK capture.

---

### User Story 3 - Ingestion Health & Verification (Priority: P3)

After setting up ingestion, the developer needs to verify the integration is working correctly. They want to confirm record counts, spot errors, and understand the shape of the data before handing it to the PM.

**Why this priority**: Without verification, developers cannot confirm that setup worked. However it adds no new user-facing behavior — it surfaces information that the system already holds internally.

**Independent Test**: Can be tested independently by querying the ingestion status endpoint after a test import and verifying it returns accurate counts, the timestamp of the last ingested record, and any error log entries.

**Acceptance Scenarios**:

1. **Given** a historical import has completed, **When** the developer checks ingestion status, **Then** they can see: total records ingested, number of records skipped (with reasons), timestamp of the most recently ingested record, and any errors encountered.
2. **Given** runtime capture has been running for 24 hours, **When** the developer checks the status, **Then** they can see: total records captured since setup, average capture volume per hour, and the timestamp of the most recent capture.
3. **Given** the field mapping configuration is invalid (e.g., references a column that doesn't exist), **When** the import is initiated, **Then** the import does not start and the developer receives a specific error identifying the misconfigured field.

---

### Edge Cases

- What happens when the source database has millions of records? The import must paginate and not load the entire dataset into memory.
- What if the source database and AnswerGuard's database are on different networks with high latency? Import should be resumable, not atomic.
- What if two SDK instances send the same Q&A pair simultaneously (e.g., in a distributed system)? Deduplication must be idempotent.
- What if the question or answer text exceeds typical database field limits (e.g., a multi-page answer)? The system must handle large text fields without truncation.
- What if the client's Q&A database uses a non-standard schema (e.g., question and answer are in the same JSON blob column)? Field mapping must support basic extraction patterns.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST read Q&A pairs from a client-specified source database using a connection string, without writing to or modifying the source database.
- **FR-002**: System MUST store ingested Q&A pairs in AnswerGuard's own database (a separate, client-provisioned PostgreSQL instance).
- **FR-003**: System MUST support configurable field mapping so developers can specify which source columns correspond to: question text, answer text, timestamp, and optional metadata fields.
- **FR-004**: System MUST deduplicate Q&A pairs using a stable identifier — either a source-provided ID or a deterministic SHA-256 hash of (question_text + answer_text + source_system_id) — so repeated imports do not create duplicate records. Timestamp is excluded from the hash to avoid drift between systems.
- **FR-005**: System MUST provide an SDK (TypeScript and Python) with a method to capture a Q&A pair at runtime, callable in a non-blocking manner.
- **FR-006**: System MUST provide a REST API endpoint for runtime Q&A capture as an alternative to the SDK, accepting at minimum: question text, answer text, optional metadata.
- **FR-007**: SDK and API capture MUST be fail-open: if AnswerGuard's storage is unavailable, the capture attempt is silently logged and the calling code continues normally without raising an error.
- **FR-008**: System MUST store the following fields per Q&A pair: question text, answer text, captured timestamp, source system identifier, ingestion method (historical vs. runtime), and an extensible metadata map for developer-provided fields (e.g., topic, session ID).
- **FR-009**: System MUST expose an ingestion status summary showing: total records stored, records skipped with reasons, last ingestion timestamp, and any errors from the most recent import run.
- **FR-010**: Historical import MUST be resumable — if interrupted, re-running it picks up from the last successfully processed batch, not from the beginning.
- **FR-011**: System MUST validate the field mapping configuration before starting an import and report specific misconfiguration errors without beginning the import.

### Key Entities

- **QAPair**: The core record. Represents one question posed to the agent system and the response it generated. Carries: unique identifier, question text, answer text, captured timestamp, source system ID, ingestion method, and a flexible metadata map.
- **IngestionRun**: Represents one execution of the historical import process. Tracks: start time, end time, records processed, records skipped, errors, and current status (running / completed / failed / resumed).
- **FieldMapping**: Configuration object that maps source database column names (or JSON paths) to AnswerGuard's standard fields. Owned by the developer at setup time.
- **SourceConnector**: Configuration for accessing the client's source database. Holds: connection string, target table/view name, field mapping, and optional filter conditions (e.g., "only import records after date X").

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can complete initial setup (configure source connector, run historical import, verify results) in under 30 minutes using only the documentation.
- **SC-002**: Historical import processes at least 10,000 Q&A records per minute on standard infrastructure.
- **SC-003**: Runtime SDK capture adds no more than 50ms of latency overhead to the agent's response path at the 95th percentile, measured end-to-end.
- **SC-004**: 100% of Q&A pairs captured via SDK or API can be retrieved from storage within 5 seconds of capture under normal conditions.
- **SC-005**: Ingestion operates with zero data loss for runtime capture: any pair successfully submitted via SDK or API is stored durably or its failure is logged — no silent drops.
- **SC-006**: Historical import uses skip-and-log behaviour: records with missing required fields (question or answer text) are skipped, logged with their index and reason in the IngestionRun error log, and the import continues. 100% fidelity is not required. The developer can inspect skipped records via the status endpoint.

---

## Assumptions

- The client's source system is BigQuery (v1 scope — other sources are out of scope).
- AnswerGuard's own storage database is also PostgreSQL, provisioned and managed by the client. AnswerGuard does not host or manage the database.
- The historical import is a one-time bulk operation followed by runtime SDK/API capture for all new records. Ongoing periodic sync from the source is out of scope for v1.
- The existing agent system can be modified to add SDK calls — it is not a black box at the integration layer.
- Q&A pairs in the source database are stored in a tabular format (relational table or queryable view). Unstructured log files are out of scope for v1.
- The LLM provider is not involved in this spec. Ingestion is a data operation only — no LLM calls are required.
- Field mapping is configured once at setup time and does not change per-record. Dynamic per-record schemas are out of scope.
- Metadata fields passed by the developer at runtime are stored as-is without validation or normalization by AnswerGuard.
- Authentication and access control for the ingestion API are handled at the infrastructure level (e.g., API key, private network). RBAC is out of scope for v1 per PRD.
